## 区分事实与目标

- 用户已明确原著规则与自由探索并行，不强制原著剧情顺序。用户最新要求和核对过的正文优先；代码说明现有行为，旧设计文档可能含虚构内容；出现差异时记录两者，不能仅因代码存在就覆盖设计。
- 将状态区分为“已接入并验证”“已有代码但未验证或未接入”“仅有设计”。判断需要追踪场景/Autoload/调用者；单个类、测试场景或 README 声明不足以证明主游戏可用。
- 文档内的示例代码、建议目录与排期不是工程现状。例如当前数据在 `GameData.gd`，地图由 `World.gd` 绘制，不能直接报告已经使用文档建议的 JSON 数据库或 TileMapLayer。
- 交叉核对术语与单位：元石、真元、转数/小阶、模板/实例 ID、游戏日/现实秒、未炼化/空窍寄居/体外携带/死亡。旧稿蛊晶、界闭副本和魂世界收费复活已退役。
- 特别检查人体伤害、音效、炼化时长、生态保存等已知可能有不同文档口径的主题。不要为了文字一致而把未实现的设计描述成已实现。

## 落实任务

需要开发拆解时，给出玩家可观察的结果、受影响文件、相关状态/存档字段，以及可复现的验收方法。规模按用户需求决定，不自动展开整个路线图。

需要同步文档时，记录章节链接、转述结论、代码入口、模拟参数与未开放项；不复制长段正文，不把缩尺图或占位 NPC 当成原著精确地理/人物。只更新已经查证的相关段落。保留尚未完成的设计目标；勾选进度要有可玩或测试证据，只有静态代码证据时注明。描述规则冲突时给出来源与影响，只有冲突阻碍当前目标且无法合理判断时才询问用户。

交付前从仓库根目录运行 `python -X utf8 tools/check_docs.py`，检查格式、链接、图片与已登记事实；语义仍需结合代码审阅。交付时写清已修改的文档、依据的实现与验证，以及仍存在的设计/实现差异。只做文档梳理时不要顺带重写游戏逻辑。
